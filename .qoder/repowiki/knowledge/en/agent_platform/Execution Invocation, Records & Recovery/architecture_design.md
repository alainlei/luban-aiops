Three cooperating layers under `agent_service/services/` implementing SPEC-037 / SPEC-063 R-4/R-5a:

- `execution_invocation.py` is the narrow coordinator (`coordinate_v3_invocation`) that enforces the register → dispatch → accept order. It never reconstructs or caches raw worker output — it only wraps it in a `VerifiedOriginal` from `execution_protocol`, then delegates secret-release permit minting to `guard.release_permit`. Failure classification uses two closed sets (`_PRE_DISPATCH`, `_UNCERTAIN`) so exceptions are never treated as proof of no-effect; outcomes are strictly `original` / `blocked` / `uncertain`.
- `execution_records.py` persists the request/receipt lifecycle (SPEC-037) with an `ExecutionRecordStore` Protocol and two backends: `InMemoryExecutionRecordStore` (dev/CI) and `PostgresExecutionRecordStore` (production). The module-level singleton `EXECUTION_RECORD_STORE` is selected via `AGENT_STATE_STORE_BACKEND` / `AGENT_STATE_DB_URL`, falls back to memory on Postgres failure, and applies a 30-day retention sweep (`RETENTION_WINDOW_DAYS`, `_SWEEP_LIMIT=100`).
- `execution_recovery.py` owns the agent-side preparation and recovery ledger against the shared `execution_runs` / `execution_intents` / `execution_observations` / `execution_dispatch_claims` / `execution_observation_state` tables. `ExecutionRecovery` is stateless except for DSN/key/epoch and uses `psycopg` directly with advisory locks (`pg_try_advisory_lock`) per run, `REPEATABLE READ` read-only transactions, and HMAC-signed cursor tokens (`_encode_cursor` / `_decode_cursor`) scoped by session/owner. `summarize_execution_recovery` and `execution_evidence_label` derive closed presentation facts without granting dispatch authority.

Dependency direction is one-way: invocation depends on protocol + worker client; recovery depends on protocol + signing + catalog; records are independent and imported by both callers. No file here touches HTTP routes directly — they expose pure functions/classes consumed by runtime kernel and route handlers.
