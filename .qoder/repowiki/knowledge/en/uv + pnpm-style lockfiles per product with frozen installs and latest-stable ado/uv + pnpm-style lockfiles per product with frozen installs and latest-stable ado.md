## Approach

The Luban workspace is a Python-first monorepo. Every backend product under `products/<name>/` declares its dependencies in a PEP 621 `pyproject.toml` using the `[project.dependencies]` list, pins compatible ranges (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`), and ships a co-located `uv.lock` generated by [uv](https://github.com/astral-sh/uv). The operator-portal SPA (`products/operator-portal/web-ui/app/package.json`) uses npm-style `dependencies` / `devDependencies` with caret ranges; no `pnpm-lock.yaml` or `yarn.lock` is present — the tree shows a checked-in `node_modules/` directory.

Builds use `uv_build` as the build backend (`[build-system].requires = ["uv_build>=0.8.14,<0.9.0"]`) and `uv sync --frozen` for dependency resolution. There is no vendored third-party source code: all packages are resolved from PyPI at install time.

## Key files

- Per-product manifests: `products/*/pyproject.toml` (Python) and `products/operator-portal/web-ui/app/package.json` (Node).
- Per-product lockfiles: `products/*/uv.lock` (generated, committed).
- Shared Makefile entry points: root `Makefile` (`sync`, `test`, `verify`) and `mk/python.mk` (`sync`, `test`).
- Root `.python-version` pins the interpreter used by uv.
- Release-note governing the policy: `docs/agentic-aiops-platform/release-notes/2026-08-28-dependency-hygiene.md` (SPEC-042).

## Architecture and conventions

### Python products

Each of the eight Python products (`agent-platform`, `audit-service`, `execution-runtime`, `identity-broker`, `incident-service`, `platform-gateway`, `skills-hub`, `tool-gateway`) follows the same layout:

- `pyproject.toml` declares runtime `dependencies` plus a `[dependency-groups].dev` group (pytest, fakeredis, etc.).
- All products require `requires-python = ">=3.11"`.
- A `uv.lock` is committed alongside the manifest.
- `Makefile` includes `../../mk/python.mk`, which defines `sync` as `uv sync --frozen` and `test` as `uv sync --frozen && OTEL_*_EXPORTER=none uv run pytest`.
- The root `Makefile.sync` loops over `PYTHON_PRODUCTS` and invokes each product's `make sync`; `make test` does the same for tests.

Dependency ranges are upper-capped to the next major version (e.g. `<3.0` for pydantic, `<1.0` for fastapi, `<7.0` for redis, `<9.0` for elasticsearch, `<51.0` for cryptography) so that a new major release is not pulled in automatically.

### Node (operator-portal)

The SPA declares `engines.node = ">=22.22.2"` (matching jsdom 30's floor) and uses caret ranges for both production and dev dependencies. The `build` script runs `tsc --noEmit && vite build`; the `test` script runs `vitest run`. The repository checks in `node_modules/`, so dependency resolution is effectively pinned by the committed tree rather than a separate lockfile.

### Version coordination

The root `VERSION` file is the single source of truth for the platform release version. The `make validate-version` target (via `shared/shared-contracts/scripts/validate_version.py`) enforces that every product's `pyproject.toml` version stays in lockstep with it. This is part of the `make verify` gate.

### Adoption policy

Per SPEC-042 and the 2026-08-28 dependency-hygiene release note, the adopted policy is **latest stable only** — no alpha, beta, RC, or dev builds. The one recorded exception is the OpenTelemetry instrumentation packages, which ship on a permanent `0.xb` channel and stay paired with their locked SDK version (e.g. `opentelemetry-instrumentation-fastapi>=0.46b0` with `opentelemetry-sdk>=1.25,<2.0`).

For the portal, deprecation regressions are guarded: vitest setup intercepts `console.error`/`console.warn` and fails teardown on any `[antd: …] deprecated` warning, making antd deprecations a hard failure.

## Conventions and constraints

- **Frozen installs**: `mk/python.mk` always runs `uv sync --frozen`, so CI and local development resolve against the committed `uv.lock` rather than re-resolving from PyPI. This is enforced by the Makefile targets.
- **No private registry configured**: grep across the repo finds no `UV_INDEX_URL`, `PIP_INDEX_URL`, `PYPI_MIRROR`, `uv.toml`, or `pip.conf`; dependencies are resolved from the default PyPI index.
- **No vendoring**: there is no `vendor/` directory and no vendored third-party source; packages are installed into `.venv/` per product.
- **Range pinning with major caps**: Python dependencies consistently declare an upper bound on the next major version (e.g. `<3.0`, `<1.0`, `<7.0`, `<9.0`, `<51.0`), preventing accidental major upgrades. This is observed in every `pyproject.toml` and codified in the hygiene release note.
- **Version lockstep**: `make validate-version` enforces that every product's declared version matches the root `VERSION` file; this is part of the `make verify` pre-commit/pre-push gate.
- **Interpreter pin**: root `.python-version` pins the Python interpreter used by uv.
- **Portal engine pin**: `package.json` declares `engines.node >= 22.22.2`, matching the `node:22-alpine` base image used by the Dockerfile.
- **Deprecation guard for antd**: the portal's vitest suite fails on any `[antd: …] deprecated` console warning, enforcing zero-tolerance migration off deprecated APIs (enforced by the test harness described in the SPEC-042 release note).
- **Build backend pin**: all Python products use `uv_build>=0.8.14,<0.9.0` as their `[build-system].requires`, keeping the build toolchain within a known range.
