# Dependency Management in the Luban Agentic AIOps Platform

## Approach

The workspace is a monorepo of nine Python services plus one Node/React SPA (`operator-portal/web-ui`). There is no top-level package manager or workspace manifest — each product owns its own dependency graph, and the root `Makefile` orchestrates them uniformly.

| Surface | Tool | Manifest | Lockfile | Resolution policy |
|---|---|---|---|---|
| Python products (8) | `uv` | `pyproject.toml` | `uv.lock` | `uv sync --frozen` (exact pin from lockfile) |
| Operator portal SPA | `npm` / `node` | `products/operator-portal/web-ui/app/package.json` | `package-lock.json` | latest stable per SPEC-042 |
| Build tooling | `uv_build` | `[build-system] requires = ["uv_build>=0.8.14,<0.9.0"]` | — | pinned range |

No vendored third-party code exists under `vendor/`, `third_party/`, or similar; all dependencies are resolved from PyPI/npm registries at build time.

## Key Files

- `mk/python.mk` — shared `sync` / `test` targets that run `uv sync --frozen` then `uv run pytest`; this is the single place enforcing frozen resolution for every Python product.
- Root `Makefile` — declares `PYTHON_PRODUCTS := agent-platform audit-service execution-runtime identity-broker incident-service platform-gateway skills-hub tool-gateway` and dispatches `make sync` / `make test` across them; also drives image builds and the `verify` gate.
- Per-product `pyproject.toml` — declares runtime `dependencies`, optional `[dependency-groups.dev]` (e.g. `fakeredis`, `pytest`), `requires-python = ">=3.11"`, and `[build-system]` pointing at `uv_build`.
- Per-product `uv.lock` — committed lockfiles generated by `uv lock`; they carry the exact transitive resolution.
- `products/operator-portal/web-ui/app/package.json` — Node entry point declaring `engines.node >=22.22.2` and the adopted React 19 / Vite 8 / antd 6 stack.
- `docs/specs/SPEC-042-dependency-hygiene/spec.md` — the authoritative policy document governing how upgrades are adopted, parked, or rejected.
- `.gitignore` — ignores `.venv/`, `node_modules/`, `dist/`, `.pytest_cache/`, etc.; **does not** ignore `uv.lock` or `package-lock.json`, so both lockfiles are tracked.

## Architecture and Conventions

### Python: ranges + locked resolutions

Runtime dependencies use PEP 440 ranges rather than exact pins in `pyproject.toml` (e.g. `agentscope>=2.0.4,<3.0`, `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `redis>=6.2,<7.0`). The actual installed versions come from the committed `uv.lock`, which is regenerated via `uv lock` to capture the latest stable version within each declared range. Development-only packages live under `[dependency-groups.dev]` and are not part of the runtime install.

Every product's Makefile includes `../../mk/python.mk`, which defines:

```
sync: ## Install/refresh this product's dependencies (frozen lock)
	uv sync --frozen
test: ## Run this product's test suite
	uv sync --frozen
	OTEL_TRACES_EXPORTER=none OTEL_METRICS_EXPORTER=none OTEL_METRICS_EXPORTER=none OTEL_LOGS_EXPORTER=none \
		uv run pytest
```

This means CI and local runs never resolve against an unfrozen lockfile — the lockfile is the source of truth for reproducible installs.

### Node: managed refresh under SPEC-042

The operator portal uses standard npm conventions (`package.json` + `package-lock.json`). Its dependency surface was refreshed by SPEC-042 to React 19, Vite 8, Vitest 4, TypeScript 5.9.x, antd 6.6.x, jsdom 30, and `@vitejs/plugin-react` 6. The spec records the full adopt set and explicitly parks TypeScript 7.x and Redis/Elasticsearch client majors with reasons.

### Version lockstep

All Python products share the same `version = "0.46.0"` in their `pyproject.toml`. The root `VERSION` file is the single source of truth, and `make validate-version` (via `shared/shared-contracts/scripts/validate_version.py`) enforces that the root version, every product version, and the portal version stay in lockstep. This is a cross-cutting invariant enforced by the `verify` target.

### Upgrade policy (SPEC-042)

The repository adopts a documented upgrade policy:

- Adopt only **latest stable** releases — no alpha, beta, RC, or dev builds.
- One recorded exception: OpenTelemetry instrumentation packages (`opentelemetry-instrumentation-fastapi`, `-httpx`, `-logging`) remain on the permanent `0.xb` channel because upstream has no stable release line for those packages while the SDK/API/exporter side is fully stable.
- Every adoption decision is recorded in the spec with a reason; parked majors must include a revisit trigger.
- Backend re-locks happen inside declared ranges; frontend component bumps follow the recorded adopt set.
- Code migration takes precedence over version pinning (e.g. antd v6 deprecation API migrations instead of downgrading).

### Enforcement points

| Rule | Enforced by |
|---|---|
| Frozen Python dependency resolution | `mk/python.mk` `uv sync --frozen` (called by every product's `sync` and `test`) |
| No prereleases anywhere | SPEC-042 R-5 acceptance criteria: "no lock resolves a prerelease" |
| All Python products share one version | `make validate-version` (root `Makefile` → `shared/shared-contracts/scripts/validate_version.py`) |
| Portal deps match adopt set | SPEC-042 R-3 acceptance criteria checked against `package-lock.json` |
| antd deprecations fail CI | SPEC-042 R-2: vitest setup fails when any `[antd: …] … is deprecated` console warning appears |
| Node engine floor respected | `package.json` `engines.node >=22.22.2` (from jsdom 30 requirement) |
| Docker base images match toolchain | Root `Makefile` `base-images` target passes `BASE_UV_*` args into `shared/base-images/base-uv/Dockerfile` |

## Constraints Observed

- Each product is self-contained: there is no top-level `pyproject.toml`, `requirements.txt`, `Pipfile`, `go.mod`, or `package.json` at the repo root.
- Lockfiles (`uv.lock`, `package-lock.json`) are committed and treated as immutable inputs to `--frozen` installs.
- Local virtualenvs (`.venv/`) and `node_modules/` are ignored; dependency state lives in the lockfile, not in checked-out environments.
- Private registries, `GOPRIVATE`, or custom index URLs were not observed in any manifest or makefile; dependencies resolve from public PyPI/npm registries.
- No vendored third-party libraries exist under version control — the tree contains only source code, tests, specs, and GitOps overlays.
