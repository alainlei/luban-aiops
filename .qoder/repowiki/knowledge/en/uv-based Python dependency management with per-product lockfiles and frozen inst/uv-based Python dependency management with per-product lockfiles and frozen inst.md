# Dependency Management in the Luban Agentic AIOps Platform

## Approach

The workspace uses **uv** (Astral) as the sole Python package manager. Each product under `products/<name>/` is an independent PEP 751 project declared via `pyproject.toml`, with a committed `uv.lock` pinning every transitive resolution. The Node/React SPA (`products/operator-portal/web-ui/app/package.json`) uses npm-style `package.json` with caret ranges; there is no `package-lock.json` visible in the tree.

There is no vendoring of third-party sources, no private PyPI registry configured at the workspace level, and no `uv.toml` / `[tool.uv]` overrides — all configuration lives in per-project files plus shared Makefile fragments.

## Key Files

- `mk/python.mk` — shared `sync` / `test` targets that invoke `uv sync --frozen` and `uv run pytest` for every Python product.
- `Makefile` — top-level orchestrator: `PYTHON_PRODUCTS := agent-platform audit-service execution-runtime identity-broker incident-service platform-gateway skills-hub tool-gateway`; `make sync` iterates them; `make verify` includes `test` among other gates.
- Per-product `pyproject.toml` — declares runtime dependencies, `[dependency-groups].dev`, entrypoint scripts, and `[build-system]` using `uv_build>=0.8.14,<0.9.0`.
- Per-product `uv.lock` — deterministic lockfile generated by uv; pinned to `https://pypi.org/simple`.
- Per-product `.python-version` — pins the interpreter (e.g. `3.12`); read by the base image's `UV_PYTHON` env var.
- `shared/base-images/base-uv/Dockerfile` — builds a minimal Amazon Linux 2023 image with a pinned `UV_VERSION=0.12.1`, sets `UV_LINK_MODE=copy`, `UV_NO_SYNC=1`, `UV_PYTHON=${PYTHON_VERSION}`, and `UV_PYTHON_INSTALL_DIR=/app/.python` so each product resolves its own interpreter.
- Per-product `Dockerfile` — copies `.python-version pyproject.toml uv.lock` and runs `RUN uv sync --frozen --no-dev`.
- `products/operator-portal/web-ui/app/package.json` — the only Node manifest, declaring React/Ant Design deps with caret ranges.

## Architecture and Conventions

1. **Per-product isolation.** Every backend service has its own `pyproject.toml` + `uv.lock`. There is no workspace-level `pyproject.toml` aggregating them; cross-product sharing happens through `shared/shared-contracts/` (schemas, policies, SQL) consumed as source code, not as packages.

2. **Semver-range constraints on runtime deps.** Runtime dependencies use upper-bound major-version caps (e.g. `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `opentelemetry-sdk>=1.25,<2.0`). Dev-only deps live under `[dependency-groups].dev` (e.g. `pytest>=8.3,<9.0`, `fakeredis>=2.26,<3.0`).

3. **Frozen installs everywhere.** Both development (`mk/python.mk`: `uv sync --frozen`) and production Docker layers (`uv sync --frozen --no-dev`) enforce exact lockfile resolution. No network resolution is allowed at build time beyond fetching the already-pinned wheels/sdists recorded in `uv.lock`.

4. **Interpreter pinning per product.** `.python-version` files (e.g. `3.12`) are copied into images alongside `pyproject.toml`; the base image defaults `UV_PYTHON=3.12` but each product can override it. `requires-python = ">=3.11"` in `pyproject.toml` is the minimum floor; `.python-version` is the actual dev/runtime target.

5. **Build backend pinned to uv_build.** All `pyproject.toml` files declare `[build-system] requires = ["uv_build>=0.8.14,<0.9.0"]` with `build-backend = "uv_build"`, ensuring reproducible sdist/wheel generation.

6. **Node side is separate.** The operator portal SPA is the only non-Python product; it uses standard npm conventions with caret ranges and no lockfile committed. Its build/test is invoked from the root Makefile via `make -C products/operator-portal test` and `web-build`.

7. **No private registries or vendoring.** `uv.lock` entries all point to `registry = "https://pypi.org/simple"`. There is no `PYPI_URL`, `index-url`, `UV_INDEX_URL`, or `--extra-index-url` anywhere in the repository. Private/internal packages (if any) would need to be added per-project.

## Conventions and Constraints

- **Rule:** All Python dependencies must be declared in `pyproject.toml` under `[project.dependencies]` (or `[dependency-groups].dev`), never via `requirements.txt` or inline `pip install` in Dockerfiles. Enforced by the Dockerfiles which copy only `.python-version pyproject.toml uv.lock README.md` and then run `uv sync --frozen --no-dev`.
- **Rule:** Lockfiles must be committed. `uv sync --frozen` will fail if `uv.lock` is missing or out of sync with `pyproject.toml`, both locally and in CI.
- **Rule:** Runtime dependencies use bounded semver ranges (`>=X,<Y+1`) to prevent accidental major-version drift. Observed consistently across `agent-platform`, `platform-gateway`, and other products.
- **Rule:** Development dependencies go exclusively under `[dependency-groups].dev`; they are excluded from production images via `--no-dev` in Dockerfiles.
- **Rule:** The Python interpreter version is pinned per product via `.python-version` and mirrored in the base image's `UV_PYTHON` default. The root `Makefile` does not set a global Python version — each product owns its own.
- **Rule:** The build backend is fixed to `uv_build>=0.8.14,<0.9.0` in every `pyproject.toml`, preventing unbounded upgrades of the packaging toolchain.
- **Constraint:** No workspace-level dependency aggregation exists; adding a new Python product means creating a new directory with its own `pyproject.toml`, `uv.lock`, `.python-version`, `Dockerfile`, and registering it in `PYTHON_PRODUCTS` in the root `Makefile`.
- **Constraint:** The Node SPA has no lockfile committed; dependency updates are unconstrained beyond caret ranges in `package.json`.
