Three sequential R4 slices that progressively harden the HITL bridge introduced in SPEC-020:
- SPEC-020 establishes the read-to-write bridge: kernel `RequireUserConfirmEvent` is translated into new v4/v5 SSE frames (`confirmation_request`, `confirmation_result`) emitted by agent-platform's streamed chat path, a `POST /api/v2/chat/confirm` endpoint with an in-memory per-session registry keyed by `confirm_id`, and a platform-gateway proxy under a new deny-by-default `chat:confirm` action. The operator portal renders an inline Approve/Deny card; decisions are recorded as a new `confirmation_decided` audit event.
- SPEC-031 adds durability and discoverability: the in-memory registry is backed by a Postgres-backed session-scoped store (same posture as SPEC-016), exposing persistent cards on the owner transcript via `GET /api/v2/sessions/{id}` and a gateway `GET /api/v1/approvals/inbox` gated by `approvals:list`. Concurrent approvals resolve exactly once with a structured `already_resolved` response rather than an opaque error.
- SPEC-032 is a portal-only UI slice: the owner's active chat view polls the existing session detail endpoint at a bounded interval while any pending card is visible, re-rendering only when state changes — no new backend surface.
Dependency direction is strictly forward: SPEC-031 depends on the bridge from SPEC-020, and SPEC-032 depends on the durable records from SPEC-031. Each spec follows the same template (status/motivation/requirements with acceptance criteria/non-goals/impact/changelog) and ties delivery to `make verify`, policy sync, and living-state doc updates.
