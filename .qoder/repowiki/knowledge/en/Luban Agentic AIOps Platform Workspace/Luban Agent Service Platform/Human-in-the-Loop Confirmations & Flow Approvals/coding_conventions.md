- Per-process singletons are exposed as module-level constants (`CONFIRMATION_REGISTRY`, `FLOW_CONTEXTS`, `FLOW_APPROVALS`, `CONFIRMATION_RECORD_STORE`) initialized at import time and documented as test-clearable but never replaced in production.
- Session-scoped stores use a private `_by_session: dict[str, T]` map with `record`/`get`/`clear`/`clear_all` methods, keeping at most one entry per session and degrading missing keys to safe defaults.
- Hot-path state is intentionally ephemeral and TTL-bounded: expiry checks use `time.monotonic()` against a captured `created_at`/`approved_at`, and expired entries raise or return `None` rather than being silently evicted.
- Durable records follow a fixed shape produced by `make_record` (confirm_id, session_id, owner_user_id, pending_calls, action, status=pending, timestamps, optional turn_index/flow_summary/approval_kind/message) and transition through the frozen set `CONFIRMATION_STATUSES = {pending, approved, denied, expired}`.
- Backend selection is driven by the `AGENT_STATE_STORE_BACKEND` env var with a factory function (`build_confirmation_record_store`) that falls back from Postgres to in-memory on failure, and each backend implements the same `ConfirmationRecordStore` Protocol.
