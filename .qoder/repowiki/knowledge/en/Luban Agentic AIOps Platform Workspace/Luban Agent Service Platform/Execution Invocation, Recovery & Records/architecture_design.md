Three cooperating layers under one concern:

- `execution_invocation.py` is the narrow async boundary (`coordinate_v3_invocation`) that enforces SPEC-063 R-4 ordering: stop check → register intent → dispatch via `handoff_original` → durably accept → mint a single-use secret-release permit. It classifies outcomes as `original`/`uncertain`/`blocked` using two closed reason sets (`_PRE_DISPATCH`, `_UNCERTAIN`) and never reconstructs worker output.
- `execution_recovery.py` owns the persistent ledger (`ExecutionRecovery`). It connects to Postgres via `psycopg`, uses advisory locks per run_id for serialization, and persists an append-only observation log (`execution_intents`, `execution_runs`, `execution_dispatch_claims`, `execution_observations`, `execution_observation_state`). Reads go through `_project`, which derives `state` (`not_dispatched` / `dispatch_claimed` / `outcome_unknown` / `result_recorded`) from the full validated observation set; paging only bounds the returned observation window. Owner-scoped reads (`owner_session_recovery`, `owner_recovery`) use HMAC-MAC'd cursors keyed by session/owner scope.
- `execution_records.py` provides a pluggable `ExecutionRecordStore` Protocol with `InMemoryExecutionRecordStore` and `PostgresExecutionRecordStore` backends, persisting the shorter lifecycle of signed requests (status `requested` → `succeeded`/`failed`/`timeout`/`rejected`) keyed by `(confirm_id, call_id)`. A module-level singleton `EXECUTION_RECORD_STORE` is selected by `AGENT_STATE_STORE_BACKEND` / `AGENT_STATE_DB_URL` and falls back to in-memory on Postgres failure.

Dependency direction is one-way: invocation depends on recovery + protocol + worker client; recovery depends on protocol + catalog + signing; records are independent and used by higher layers. Neither layer authorizes remote effects — only acknowledged writes do.
