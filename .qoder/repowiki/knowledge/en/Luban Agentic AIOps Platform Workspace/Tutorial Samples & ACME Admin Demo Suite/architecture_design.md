Two layers coexist here: (1) `deploy-samples.sh` is the sole coupling to the platform — it discovers any directory under `samples/<category>/` that contains a `skill/` subdirectory, packs those `*.md` files into the `skills-samples` ConfigMap, and restarts `skills-hub` so the generic `samples` source re-ingests them; (2) `acme-admin/` is a complete sample category containing both the target application (`app/`, a FastAPI service with in-memory store, JSON API in `api.py`, HTML pages in `pages.py`, auth in `auth.py`, assembled in `main.py`) and six skill demonstrations (`health-check`, `user-status`, `lock-unlock-user`, `password-reset`, `adhoc-password-reset`, `skill-graduation`) plus a composition runbook. Each skill follows the canonical layout `README.md` + `WALKTHROUGH.md` + `skill/*.md` + `demo/demo.sh`; `skill-graduation` intentionally ships no `skill/` because its demo produces the skill artifact at runtime. The suite's shared plumbing lives in `demo-lib.sh` and `demo-suite.sh`, which runs the four-rung ladder then asserts the cross-skill claim (HTTP mutation visible over the rendered HTML). Deployment manifests live in `acme-admin/deploy/` (kustomization, deployment, service, networkpolicy) and are applied via `make deploy-sample-app` / `make undeploy-sample-app`. Dependency direction is strictly tutorial → platform: the base overlay never names a specific sample, and samples depend on platform resources (browser-dev profile, credential sets, NetworkPolicy) only through documented prerequisites.
