Three cooperating service modules under `platform_gateway.services`:
- `token_verifier.py` performs local RS256 JWT verification against a cached `PyJWKClient` (recreated when `identity_jwks_url` changes) and maps decode errors to the domain `TokenVerificationError`, returning an `IdentityContext`.
- `gateway_service.py` is the orchestration layer: it resolves identity (`resolve_request_identity`), enforces policy (`enforce_policy` → `policy_engine.evaluate`), and exposes one async function per upstream operation (session CRUD, document CRUD, skill draft/graduate, approvals inbox, chat/stream). Each proxy wraps `agent_client.*` with a uniform error posture — upstream 4xx pass through verbatim, transport failures and upstream 5xx become HTTP 502 — and emits audit events via `audit_emitter.build_audit_event` / `emit_audit_event`.
- `delegation_client.py` implements per-replica, per-user delegated-token caching (`DelegationClient`) backed by an exchange call to `identity_service_url/api/v1/auth/exchange`. It prefers a projected workload token from disk (SPEC-009 R-3) and falls back to static client credentials; in dev mode it signs its own subject token with an RSA key loaded or generated at `dev_signing_key_path`. The module-level singleton `_delegation_client` plus `get_delegation_client()` / `reset_delegation_state()` gives callers a process-scoped cache keyed by `subject`.

Dependency direction is one-way: `gateway_service` depends on both `token_verifier` and `delegation_client`; neither of those two depends on the gateway. All three depend only on `PlatformGatewaySettings`, `schemas.api.IdentityContext`, and shared `core.metrics` counters (`record_token_verification`, `record_policy_decision`, `record_delegation_exchange`, `record_delegation_cache`).
