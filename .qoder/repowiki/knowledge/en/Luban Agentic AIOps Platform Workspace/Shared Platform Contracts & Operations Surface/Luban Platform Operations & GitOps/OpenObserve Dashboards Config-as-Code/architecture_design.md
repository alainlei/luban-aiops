Two-layer split between immutable config artifacts and tooling:
- `*.dashboard.json` files are OpenObserve v5+ importable JSON (envelope: `version`/`dashboardId`/`title`/`tabs[]`/`variables`/`defaultDatetimeDuration`) consumed by the platform's OTel push mirror (`OTEL_MIRROR_FAMILIES` in each service's `core/metrics.py`).
- `validate_dashboards.py` is the offline `make verify` gate: it parses every dashboard JSON, enforces the OpenObserve envelope and panel schema, then AST-scans all `products/*/src/*/core/metrics.py` to build an emitted-metric catalog and cross-checks every PromQL/SQL reference against it — no imports, no network.
- `apply-dashboards.sh` is the live operator step: it calls OpenObserve's `/api/{org}/dashboards` REST API with Basic auth (`OO_ROOT_USER_EMAIL`/`OO_ROOT_USER_PASSWORD`), fetches the existing list once, then POSTs or PUTs per file by stable `dashboardId`, failing loudly on the first rejected dashboard.
- Dependency direction is one-way: dashboards depend on emitted metrics; validation depends on both; the apply script only talks to OpenObserve. The README documents the two-surface model (SPEC-005) and the separation of `make validate-dashboards` (verify) vs `apply-dashboards.sh` (operator/R-4).
