# Dependency Management in Luban Agentic AIOps Platform

## Approach

The repository uses **uv** (Astral's Python package manager) as the single dependency resolver across all eight backend services and the acme-admin sample app. There is no Poetry, pipenv, or `requirements.txt` anywhere. The frontend operator portal (`products/operator-portal/web-ui/app/package.json`) uses npm for its SPA; this card focuses on the Python side.

Each product under `products/<name>/` owns its own:
- `pyproject.toml` — declares `[project]` dependencies with semver-compatible ranges and a `[dependency-groups.dev]` section for test-only packages.
- `uv.lock` — fully pinned lockfile generated by uv, committed to version control.
- `.python-version` — pins the interpreter (all products use `3.12`).
- `Dockerfile` — installs deps via `RUN uv sync --frozen --no-dev`, so production images never resolve from PyPI at build time.

The root `Makefile` aggregates per-product routines: `make sync` iterates over `PYTHON_PRODUCTS := agent-platform audit-service execution-runtime identity-broker incident-service platform-gateway skills-hub tool-gateway` and invokes each product's `sync` target, which delegates to `mk/python.mk`.

## Key Files

- `mk/python.mk` — shared `sync` / `test` targets that run `uv sync --frozen` then `uv run pytest`.
- `mk/image.mk` — shared container-image targets used by every product Dockerfile.
- `shared/base-images/base-uv/Dockerfile` — shared base image pinning `UV_VERSION=0.12.1` and `PYTHON_VERSION=3.12`; sets `UV_NO_SYNC=1`, `UV_LINK_MODE=copy`, `UV_PYTHON_INSTALL_DIR=/app/.python` so the runtime layer stays immutable after `uv sync`.
- Root `Makefile` — defines `PYTHON_PRODUCTS`, `IMAGE_PRODUCTS`, and the `sync`/`build`/`push` orchestration.
- Each `products/*/pyproject.toml` — dependency declarations (e.g. `agent-platform/pyproject.toml` pins `agentscope>=2.0.4,<3.0`, `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, etc.).
- Each `products/*/uv.lock` — committed, deterministic lockfile (e.g. `agent-platform/uv.lock` has `version = 1`, `revision = 3`, `requires-python = ">=3.11"`, and exact resolved versions like `agentscope==2.0.8` sourced from `https://pypi.org/simple`).
- Each `products/*/.python-version` — interpreter pin (all `3.12`).
- Each `products/*/Dockerfile` — `RUN uv sync --frozen --no-dev` (or `--no-install-project` in some variants).

## Architecture & Conventions

1. **Per-product lockfiles, not workspace-level.** There is no root `uv.lock`. Each product resolves and pins its own transitive closure independently. This allows different products to tolerate different major-version bounds (e.g. `fastapi>=0.115,<1.0` vs. `>=0.115,<1.0` across services).

2. **Semver-compatible ranges in `pyproject.toml`, exact pins in `uv.lock`.** Dependencies are declared with upper-bound major/version caps (e.g. `<3.0`, `<1.0`, `<4.0`) to allow patch/minor updates while blocking breaking changes. The lockfile records the exact resolved version and SHA-256 hashes for both sdist and wheels.

3. **Frozen builds everywhere.** Both local dev (`uv sync --frozen` in `mk/python.mk`) and production Docker builds (`uv sync --frozen --no-dev` in every product Dockerfile) refuse to resolve new versions. A stale lockfile causes an immediate failure rather than silently drifting.

4. **Shared base image strategy.** All backend images derive from `shared/base-images/base-uv`, which installs a pinned `uv` binary and a pinned Python interpreter into `/app/.python`. The image sets `UV_PYTHON=${PYTHON_VERSION}` (default `3.12`) and `UV_PYTHON_INSTALL_DIR=/app/.python` so `uv sync` installs packages into a deterministic location owned by the non-root `app` user (uid 1000). The base image is built via `make base-images` using `BASE_UV_UV_VERSION` and `BASE_UV_PYTHON_VERSION` from `mk/defaults.mk`.

5. **No private registry configured.** All resolved packages in the lockfiles show `source = { registry = "https://pypi.org/simple" }`. There is no `PYPI_URL`, `UV_INDEX_URL`, `PIP_INDEX_URL`, or `GOOGLE_APIS_KEY` pointing at a corporate index. Private packages would need to be added to PyPI or mirrored externally.

6. **Build system pinned separately.** `pyproject.toml` `[build-system].requires = ["uv_build>=0.8.14,<0.9.0"]` pins the build backend itself, ensuring reproducible wheel building.

7. **Frontend dependencies isolated.** The operator portal SPA lives under `products/operator-portal/web-ui/app/` and uses npm/pnpm (package.json + node_modules); it is not part of the uv ecosystem and is excluded from `PYTHON_PRODUCTS`.

## Conventions & Constraints

- **Every Python product must have a `pyproject.toml` plus a committed `uv.lock`.** Enforced by `make sync` iterating `PYTHON_PRODUCTS` and failing if any product's Makefile (which includes `mk/python.mk`) cannot run `uv sync --frozen`.
- **Production images must use `uv sync --frozen --no-dev`.** Observed uniformly across all product Dockerfiles; removing `--frozen` would break reproducibility.
- **Interpreter version pinned per product via `.python-version` and mirrored in the base image.** The base image's `UV_PYTHON=3.12` matches the product `.python-version` files.
- **Dependency ranges must cap the next major version.** All observed ranges follow `>=X.Y,<Z.0` (e.g. `agentscope>=2.0.4,<3.0`, `fastapi>=0.115,<1.0`, `pydantic>=2.8,<3.0`, `redis>=6.2,<7.0`, `psycopg[binary]>=3.2,<4.0`). This is a convention in the codebase, not enforced by a linter.
- **Dev dependencies go in `[dependency-groups.dev]`, not `[project.dependencies]`.** Observed in every `pyproject.toml` (e.g. `fakeredis`, `pytest`). They are excluded from production images via `--no-dev`.
- **Base image rebuilds require `make base-images` before `make build`.** The root `build` target depends on `base-images`, which rebuilds `shared/base-images/base-uv` with the current `BASE_UV_*` defaults from `mk/defaults.mk`.
- **No vendoring of third-party source.** All dependencies are pulled from PyPI at resolution time and cached by uv; nothing is checked into `vendor/` or similar.
- **Lockfiles are the source of truth for CI.** The `verify` gate runs `make test` (which calls `uv sync --frozen`) across all Python products, so any drift between `pyproject.toml` and `uv.lock` fails CI.
